## بخش الف — عملکرد: چرا WhatsApp کند است

### الف-۱) فاقد FakeIP: تندانه‌ی DNS سرد، صف‌به‌صف از **داخل تونل** *(رفع‌شده)*

**مشکل.** هنگام شروع سرد، WhatsApp حدود ۱۵ دامنه را از DNS می‌پرسد. بدون FakeIP، هر یک از
این پرسش‌ها به‌عنوان پرسش «عمومی» به گراف DoH می‌افتد:

- **Xray:** `dns.servers` = [سرورهای bootstrap با دامنه‌ی `full:node` + `skipFallback`] و
  سپس DoHهای رمزنگاری‌شده **از طریق پراکسی انتخاب‌شده**. پرسش‌های A/AAAAی که به هیچ
  سرور دامنه‌محوری نخورند، به همین DoHهای دور می‌روند — یعنی **هر پرسش DNS یک RTT کامل
  از تونل** می‌خورد، و این درحالی است که تونل هنوز گرم نشده.
- **sing-box:** `final: dns-remote` یعنی دقیقاً همین: هر دامنه‌ای که به هیچ قاعده‌ای
  نخورده باشد، با DoH از داخل تونل حل می‌شود.

نتیجه: UI اپ می‌توانست فوراً شروع کند، ولی نمی‌توانست؛ «اول DNS، بعد اولین بایت».

**اصلاح اعمال‌شده (هر دو هسته، زیر کلید `dnsFakeIpEnabled` که پیش‌فرض روشن است):**

Xray (`XrayConfigHardener.kt`):
1. بلوک سطح‌بالا `fakedns` با اسکیمای JSON دقیقِ `v26.9.9` (`infra/conf/fakedns.go`):
   ```json
   "fakedns": { "ipPool": "198.19.0.0/16", "poolSize": 65535 }
   ```
   (کلید JSON `poolSize` است، نه `lruSize`. محدودیت `app/dns/fakedns/fake.go`:
   `log2(lruSize) < تعداد بیت خالی زیرشبکه`؛ در /16 مقدار 65535 معتبر است ولی 65536
   رد می‌شود. نیمه‌ی دوم بلوک رزروشده‌ی benchmark یعنی `198.19.0.0/16` انتخاب شد تا
   ضمن غیرعمومی‌بودن، با آدرس رابط TUN یعنی `198.18.0.1/32` **تصادف** نداشته باشد.)
2. نام‌سرور `{"address":"fakedns","queryStrategy":...}` به‌عنوان **اولین سرور عمومی**
   (قانون `verify()`: هر آیتم `dns.servers` باید `queryStrategy` یک‌شکل داشته باشد).
   لیستگرهای bootstrap دامنه‌محور هستند و در `sortClients` همیشه اولویت دارند، پس
   نام‌نود دست‌نخورده می‌ماند.
3. `destOverride` اسنیفینگ = `["http","tls","quic","fakedns"]`. اسنیفر `fakedns` دامنه را
   **بدون انتظار پیکربندی** (SniffMetadata روی payload خالی) بازیابی می‌کند و — تأییدشده
   روی `app/dispatcher/default.go` — حتی با `routeOnly: true` هدف به دامنه‌ی واقعی
   جایگزین می‌شود (`protocol != "fakedns" && !isFakeIP` در شرط RouteOnly نیست).
4. **هیچ قانون روتینگ `fakedns` نوشته نمی‌شود:** پروتوی `RoutingRule` در `v26.9.9` چنین
   فیلدی ندارد و قانون `{"type":"field","fakedns":true}` خطای parse برای فیلد ناشناخته
   است. آدرس‌های فیک از قاعده‌ی `final` (پراکسی انتخاب‌شده) عبور می‌کنند — قاعده‌ی
   «نقاط‌سنجی روتینگ روی پراکسی انتخابی بماند» دست‌نخورده است. IP ruleها (geoip:ir)
   روی **IP واقعی** کار می‌کنند چون `features/routing/dns/context.go` دامنه‌ی بازیابی‌شده
   را با `FakeEnable:false` حل می‌کند.

sing-box (`SingBoxConfigBuilder.kt`):
1. سرور DNS شکل ۱.۱۴ (بلوک قدیمی `dns.fakeip` در ۱.۱۴ حذف شده):
   ```json
   { "type": "fakeip", "tag": "dns-fakeip", "inet4_range": "198.19.0.0/16" }
   ```
   `inet4_range` اجباری است (بدون آن `NewTransport` خطا می‌دهد). فقط v4 فعال است:
   پرسش AAAA از استخر v4، پاسخ «موفق/خالی» می‌گیرد و اپ به رکورد A برمی‌گردد.
2. قاعده‌ی DNS `{"query_type":["A","AAAA"],"action":"route","server":"dns-fakeip"}` —
   **پس از** قاعده‌ی نام‌نود (bootstrap باید برتر بماند).
3. قاعده‌ی روت `{"action":"resolve"}` **اجباری** شد (همیشه با fakeip). دلیل از
   `route/route.go`: فلوِ بازیابی‌شده در pre-match با مقصدِ **دامنه** می‌رسد و
   `preMatchFlow` آن را با پیام «a resolve action is required before routing to outbound»
   **رد می‌کند** مگر `DestinationAddresses` پر شده باشد. resolve برای مقاصد IP بی‌اثر است.
4. **`final` همان `dns-remote` می‌ماند** و حلقه‌ی فیک وجود ندارد: در مسیرهای حل
   «خودِ موتور» (دایل پراکسی و action resolve) روتر قوانین را با
   `allowFakeIP=false` می‌پیماید (`lookupWithRulesType`) و ترنSPORT fakeip رد می‌شود؛
   دامنه‌های ایرانی با قاعده‌ی geosite به `dns-direct` (ریज़ولور محلی) و بقیه با DoH از
   تونل حل می‌شوند. خروجی: پراکسی همیشه **آدرس واقعی** را دایل می‌کند.

**چرخه‌ی کامل (هر دو هسته):** پرسش اپ → پاسخ آنی محلی (فیک) → بسته به 198.19.x از TUN →
بازیابی دامنه → روتینگ (IP ruleها IP واقعی می‌بینند) → پراکسی → دایل با آدرس واقعی از
داخل تونل. پرسش‌های DNS دیگر «در مسیر اتصال» نیستند؛ حلقه‌ی حل واقعی با هر دامنه یک‌بار
و کش‌شده انجام می‌شود.

**کنترل:** کلید روشن/خاموش در تنظیمات ← شبکه (پشت «رهگیری DNS سنتی») با ترجمه‌ی فارسی.
در هر دو هسته، زنجیره فقط وقتی رهگیری DNS روشن است فعال می‌شود؛ بدون قاعده‌ی رهگیری
پورت ۵۳ پاسخ فیک اصلاً به اپ نمی‌رسد. در Xray اسنیفینگ نیز باید روشن باشد، چون بدون آن
بازیابی دامنه ممکن نیست و پراکسی آدرس فیک را دایل می‌کرد. نمونه‌ی rank و delay-test
هیچ‌گاه fakeip ندارند (در `hardenForNativeRank` صریحاً strip می‌شود). در sing-box، وقتی
cache file روشن است `store_fakeip` نیز نوشته می‌شود تا پاسخ کش‌شده‌ی اپ پس از راه‌اندازی
مجدد هسته به reverse mapping گم‌شده نخورد.

### الف-۲) `heal()` روی پینگِ صرفاً بالا، Fragment فعال می‌کرد *(رفع‌شده)*

**مشکل.** `DpiEvasionPolicy.heal()` (آخرین مرحله‌ی `effectiveSettings`) روی شواهد
`highPing` (پینگ ≥ ۲۵۰ms — برای مسیرهای رله‌ای بین‌المللی **عادی** است) کارکردن زیر
را برمی‌انگیخت:

```kotlin
evidence.highPing -> if (current.rank >= RECORD_SPLIT.rank) current else RECORD_SPLIT
```

یعنی **هر** حلقه‌ی TLS جدید را به تکه‌های ۱۰–۳۰ بایت با pacing ۱۰–۲۰ms خُرد می‌کرد
(RECORD_SPLIT) و سقف MTU را ۱۴۰۰ قفل می‌کرد. پهنای‌باند/فاصله مشکلات DPI نیست؛ خُردکردن
نه کمک می‌کند، بلکه **هزینه‌ی هر دست‌دستی** را چند برابر به‌بالا می‌برد. WhatsApp برای هر
فلو (سگنالینگ، هر جریان WebRTC) یک handshake تازه دارد — یعنی هر فلو چند ثانیه pacing
یک‌بایتی می‌پرداخت.

**اصلاح اعمال‌شده** (`DpiEvasionPolicy.kt`): fragment/MTU-ceiling فقط با **عیب packet-level** (lossy یا highJitter) فعال می‌شود؛ `highPing` تنها بودجه‌ی زمانی
(`benchTimeoutSec ≥ 14`، `tcpPrecheckTimeoutMs ≥ 3000`) می‌گیرد که اصلاح واقعیِ لینکِ
کند است. رفتار lossy (`MAX_SLICE` + `muxUdp443=reject`) و highJitter
(`RECORD_SPLIT`/`TLSHELLO_SNI`) دست‌نخورده ماند. دو تست نوسان新增:
`healDoesNotFragmentOnPlainHighPing` و `healStillEscalatesOnJitter`.

### الف-۳) MTU و پراکنده‌سازی *(بررسی‌شده — بدون تغییر)*

سیاست MTU فعلی (سقف ۱۴۲۰ سیم‌کارتی / ۱۳۸۰ hy2-kcp-quic / ۱۲۸۰ بحرانی + یادگیری
تطبیقی) منطقی است؛ مشکل واقعی «سقف ۱۴۰۰ِ ری‌اکتیو روی پینگ بالا» بود که با الف-۲ رفع شد.
کاهش MTU ۱۰۰ بایت ≈ ۷٪ پیکر بیشتر = هزینه‌ی خالص بدون عائد روی لینکِ کند ولی پایدار.

### الف-۴) handshake تازه برای هر فلو UDP + mux خاموش *(بررسی‌شده — عمداً بدون تغییر)*

VLESS-over-TCP هر فلو UDP را یک جریان TLS تازه حمل می‌کند. mux (Salamander/H2M) می‌تواند
آن‌ها را multiplex کند، اما:
- موز خراب‌کننده‌ی شناخته‌شده‌ای برای بعضی endpointهاست و کلید زور باز کردن آن
  «بهینه‌سازی» نیست؛
- `adaptiveMuxEnabled` پیش‌فرض روشن است و موتور Benchmark وقتی شواهد بدهد
  (`testCandidate`: latency≥120 یا learned + thermal≥0.60) mux را برمی‌دارد.
دریافت‌شده: mux را به پیش‌فرض نمی‌بریم؛ زنجیره‌ی تطبیقی همین کار را با شواهد می‌کند.

### الف-۵) IPv6 *(بررسی‌شده — بدون تغییر)*

`ipv6Enabled + preferIpv6` پیش‌فرض روشن است و `AddressFamilyPolicy` در هر شبکه با
شواهدِ خودِ نود تصمیم می‌گیرد (پایین‌سازی per-session)؛ با FakeIP، AAAA خالی/واقعی
هر دو مسیری سالم دارند (Xray: پاسخ خالی فیک → fallthrough به DoH واقعی؛ sing-box:
پاسخ موفق/خالی). دست‌نخورده ماند.

## بخش ب — نقد UI/UX (اولویت‌بندی)

### ب-۱) خوانایی فارسی: کف ۱۰.۵sp و وزن نازک Vazir *(رفع‌شده)*

**مشکل.** `labelSmall = 10.5sp` هم پایین‌تر از مشخصه‌ی Material 3 (11sp) بود و هم
پایین‌تر از اندازه‌ای که ترکیب‌های نازک Vazirmatn روی پنل‌های میانی‌رده خوانا می‌ماند.
علاوه بر این، `bodyMedium/bodySmall` با وزن Regular رندر می‌شد؛ Vazir Regular برشِ
نمایش است و در ۱۴sp روی AMOLED/سطوح روشن محو می‌شود.

**اصلاح اعمال‌شده** (`AetherTheme.kt`): کف `labelSmall` به 11sp (فارسی 11.5sp با line
height 16sp) و وزن بدنه‌ی فارسی به Medium. چیدمان‌ها جابه‌جا نمی‌شوند (نیم تا یک sp).

### ب-۲) دوخطه بودن: `fontFamily=sans` پلتفرم در برابر Vazirmatn *(رفع‌شده)*

**مشکل.** `styles.xml` فونت پلتفرم `sans` (Roboto) داشت: پنجره‌ها، toast، کرونمای IME
و هر سطح غیر-Compose با فونتِ متفاوت از بقیه‌ی محصول رندر می‌شد — محصولِ دوخطه.

**اصلاح اعمال‌شده**: `android:fontFamily = @font/vazirmatn_medium` (minSdk 26؛ font
resource در theme XML از API 26 معتبر است). Vazirmatn هر دو برش فارسی/لاتین دارد.

### ب-۳) سلسله‌مراتب بصری: orb 92dp تنها کنترل اولیه *(نقد + پیشنهاد)*

`ConnectionCore` (L3297) دایره‌ی 92dp تنها عمل اصلی صفحه است و بقیه (پینگ، سرور،
آمار) حاشیه‌ی آن. در تم‌های iOS-styled این «هویی‌سازی» عمداً است، ولی در تم Modularity
و روی صفحه‌های بزرگ، سلسله‌مراتبِ اطلاعاتی ضعیف می‌شود: کاربر «وضعیت اتصال» را باید از
رنگِ orb بخواند نه از تِکستی ساختاری. **پیشنهاد (اجرا نشد):** باند وضعیت اتصال به‌عنوان
سطح یک‌ام (text-first) و orb به نقشِ ثانویه در همه‌ی تم‌ها — تغییر بزرگِ چیدمانی که با
invariantهای CI (Prism UI) نیاز به بازطراحی آگاهانه دارد.

### ب-۴) معماری اطلاعات تنظیمات: ۵ تب *(نقد + پیشنهاد)*

`SettingsWorkspaceTab` = General / Tests / Network / Engine / System. قلم‌های کلیدی
پخش‌شده‌اند: per-app routing و DNS در **Network**، fragment/mux در **Engine**،
MTU/آگاه‌سازی در تب‌های دیگر. یک کاربر که می‌خواهد «DNS اپ‌ها را فیک کند» سه تب می‌بازد.
**اصلاح اعمال‌شده (محدود):** کلید Fake IP کنار «رهگیری DNS سنتی» در تب Network — همان
جایی که ذهن کاربر می‌رود. **پیشنهاد (اجرا نشد):** تب Network را «مسیر + DNS» و Engine را
«حمل + DPI» با قلم‌های گروه‌بندی‌شده بازنویسی کند؛ invariantهای CI معماری فعلی را
«انعطاف‌پذیر» اما نه اجباری می‌دانند، پس امکان‌پذیر است.

### ب-۵) الگوی تعامل NodeCard: ضربه=اتصال، swipe=ویرایش *(نقد)*

در Servers، ضربه‌ی روی کارت = اتصال و کشیدن = ویرایش. با کارت‌های مارکی‌دار (اسمِ
بریده‌شده) و پینگ‌کپسول، هدفِ «فقط ببینم» و «اتصال» یکی شده‌اند؛ خطای «اتصالِ تصادفی
به نودِ اشتباه» در لیستهای بلند هزینه دارد. **پیشنهاد (اجرا نشد):** ضربه = انتخاب/جزئیات
(برگه)، اتصال از دکمه‌ی مشخص روی برگه؛ یا حفظ ضربه=اتصال با تأخیر 200ms + امکان
لغو (kinetic).

### ب-۶) رشته‌های انگلیسیِ بی‌ترجمه *(نقد + الگوی درست)*

`trx()` روی **لیتِ럴 دقیق** کار می‌کند؛ هر رشته‌ی **پویا** (شمارنده، نرخ، زمان، کامپوز)
در حالت فارسی انگلیسی رندر می‌شود. الگوی درست: الگوهای پایین `faTranslate`
(`faPattern`) را برای رشته‌های پویا گسترش داد — مثال، `"PING: 142 ms"` → الگوی اعداد.
اجرا در این PR نکردیم (سطحِ گسترشِ واژگانِ جداست) ولی کلیدِ جدیدِ Fake IP از همان
لحظه با دو ورودیِ واژگانی فارسی آمده است.

### ب-۷) رنگ و کنتراست *(نقد)*

`inkFaint` در تم روشن = Navy با آلفای 42٪ ≈ نسبت کنتراست 3.2:1 — زیر آستانه‌ی AA برای
متنِ کوچک. به‌عنوان رنگِ «فنی/ثانویه» پذیرفته‌شده است، ولی برای captionهای برچسب‌دار
(همان `labelSmall`) ترکیبش با ب-۱ خراشی بود؛ با بزرگ‌شدن کف اندازه، آسیب کمتر شد.
**پیشنهاد:** `inkFaint` را به 50–55٪ برسانیم — یک خط، ریسک صفر.

## راستی‌آزمایی

- **تست‌های واحد:** `FakeIpV184Test` (اعتبار و ظرفیت CIDR مشترک، شکل Xray
  روی/خاموش/بدون اسنیفینگ/rank، شکل sing-box روی/خاموش، ترتیب bootstrap، و خاموش‌ماندن
  هر دو هسته بدون DNS interception) + ۲ تست heal در `DpiEvasionPolicyTest`. تست قدیمیِ
  اسکیمای DNS sing-box نیز اکنون `fakeip` را درست به‌عنوان transport بی‌نیاز از کلید
  upstreamِ `server` می‌شناسد؛ transportهای راه‌دور همچنان اجباراً کلید ۱.۱۲ را دارند.
- **invariantهای CI (verify.yml):** رشته‌های پین‌شده (`Unmatched routing fallback must
  stay on the selected proxy`، `normalizeGeoSiteTag(settings.routeAdsTag)`، مارکرهای
  Prism UI و `Marble Product UI v9.1.0`) همه دست‌نخورده‌اند؛ درج‌های UI فقط «اضافه»
  هستند و هیچ مارکری حذف نشده.
- **هسته‌ها:** هیچ‌گونه تغییر در `core-lock.json`؛ شکل‌های JSON دقیقاً از سورسِ پین‌شده
  استخراج‌شده (Xray `infra/conf/fakedns.go` / `app/dns/nameserver.go` /
  `app/dispatcher/default.go` / `app/router/config.proto`؛ sing-box
  `dns/transport/fakeip/*` / `dns/router.go` / `route/route.go` / `option/rule_dns.go`).
